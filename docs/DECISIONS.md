# Decisiones arquitectónicas aprobadas

1. **Dos clientes en un workspace pnpm.** Desktop usa Tauri 2; Web usa Vite con soporte PWA. Comparten `domain`, `application`, `ui` y `features` para evitar duplicación.
2. **Persistencia por plataforma.** SQLite local es la fuente primaria de operación de Desktop. Supabase/PostgreSQL es la fuente central compartida para Web; las lecturas cliente están sujetas a autenticación y RLS.
3. **Separación mediante puertos.** `application` define contratos; cada app aloja su adaptador concreto. `domain` permanece en TypeScript puro, sin React, Tauri, SQLite ni Supabase.
4. **Modelo incremental.** Sprint 1 creó `app_meta`; Sprint 2 añade solo Business, Branch y Device. Las entidades futuras considerarán `business_id`, `branch_id` y, para sincronización, `device_id` cuando corresponda.
5. **Sincronización diferida hasta Sprint 5.** Los primeros sprints documentaron Desktop SQLite ↔ Supabase sin implementarlo. Sprint 5 lo concreta únicamente para Customer.
6. **Sucursal obligatoria para Device.** Cada Device pertenece a una Branch del mismo Business; una FK compuesta impide vínculos cruzados. No hay razón actual para permitir dispositivos sin sucursal.
7. **Identificadores y tiempos.** UUID generables localmente permiten identidad offline. Cloud guarda `timestamptz`; Desktop guarda UTC ISO 8601. La instalación Desktop posee un UUID persistente separado del ID del registro Device.
8. **RLS cerrada hasta autenticación en Sprint 2.** Las tablas Cloud habilitaron RLS y revocaron acceso a `anon` y `authenticated`. La migración de autenticación concede únicamente lectura bajo políticas por membership. El seed se limita a desarrollo y no se aplica automáticamente al remoto.
9. **Bootstrap Desktop provisional de Sprint 2.** El adaptador local puede crear CentroColor, Sucursal principal y Device locales, pero dejó de ejecutarse al abrir la UI tras incorporar autenticación. Las filas anteriores se conservan; el contexto autorizado actual usa IDs Cloud.
10. **Identidad Cloud y límite multiempresa.** Supabase Auth identifica usuarios; memberships activos otorgan acceso a negocios y portan uno de tres roles iniciales. En las tablas de identidad, el cliente solo lee bajo RLS. El alta y cambio de roles son tareas administrativas manuales por ahora.
11. **RLS sin recursión.** Un helper en esquema `private`, con `SECURITY DEFINER`, `search_path` vacío y `auth.uid()`, comprueba membership activo. El esquema no se expone por API y la función solo se concede a `authenticated`.
12. **Autorización offline Desktop.** Tras login Cloud exitoso se guarda un resumen del contexto en SQLite; el siguiente inicio lo usa explícitamente como `offline-authenticated`. No se guarda sesión/token Desktop, por lo que revalidar exige login online. La copia local puede quedar obsoleta por revocación remota y no tiene protección de RLS.
13. **Clientes como primera entidad operativa.** Customer y sus reglas viven en domain; application define un único puerto y casos de uso. Web usa Supabase bajo RLS y Desktop usa SQLite local. La UI compartida recibe el puerto, usa el BusinessContext y limita la lista a 100 filas.
14. **Referencia local a negocio autorizado.** `customers.business_id` en Desktop no tiene FK a `businesses` local: el contexto validado trae IDs Cloud que pueden no coincidir con las entidades provisionales locales. Los adaptadores filtran toda operación por negocio. La migración Cloud sí tiene FK y RLS.
15. **Outbox atómico y acotado.** SQLite registra cambios Customer mediante triggers en la misma sentencia de escritura. Una fila por entidad compacta mutaciones consecutivas; `local_revision` impide reconocer por accidente una edición posterior al push. La infraestructura tiene campos mínimos reutilizables, pero solo sincroniza Customer.
16. **Versión Cloud y conflictos explícitos.** PostgreSQL gobierna `customers.updated_at`; Desktop guarda la última versión Cloud conocida y compara antes de actualizar. Los cambios concurrentes crean un conflicto local, sin sobrescritura silenciosa. La UI permite elegir la versión local o Web consultando Cloud de nuevo; conservar local usa comparación optimista otra vez.
17. **Pull incremental por negocio.** Cursor persistido `(updated_at, id)` y páginas limitadas. PostgreSQL asigna versiones monotónicas bajo un bloqueo de fila en `private.customer_sync_clock` por negocio para que el orden de commit no deje huecos; el cursor compuesto también cubre empates de filas previas. El cursor avanza después de aplicar o registrar cada fila. La sesión Cloud y el membership se revalidan antes de cada ciclo; el contexto offline permite operar SQLite, pero no sincronizar.
18. **POS local primero.** Sprint 5 opera Product, ProductCategory, Sale y SaleItem en SQLite Desktop. El esquema Cloud existe para evolución futura, sin adaptador Web ni sincronización de estas entidades. `sync_outbox` y el indicador existente continúan siendo exclusivos de Customer.
19. **Ventas atómicas e históricas.** El comando Tauri `complete_local_sale` escribe Sale y SaleItems en una transacción SQLite con validación de suma y foreign keys. Los ítems guardan snapshots de nombre, barcode y precio; ventas completadas no se editan. La referencia visual es un prefijo de UUID, sin semántica fiscal ni secuencia Cloud.
20. **Centavos enteros y stock diferido.** Los contratos usan enteros seguros de centavos y la entrada decimal se convierte mediante BigInt. Product no incluye stock global; Sprint 6 lo modelará por sucursal. El `device_id` de Sale es nullable hasta disponer de una asociación confiable entre instalación y Device Cloud.
21. **FK multiempresa de Sale a Device.** La migración Cloud pendiente agrega una UNIQUE explícita `(business_id, id)` a `devices` para respaldar la FK compuesta de `sales`. La PK de `devices.id` garantiza unicidad lógica del par, pero PostgreSQL exige una clave única explícita sobre las columnas referenciadas. Se conserva así la comprobación de pertenencia del dispositivo al negocio sin alterar la migración de identidad ya aplicada.
22. **Paridad permanente Desktop/Web.** Ambos clientes son el mismo sistema. Una capacidad importante debe existir en ambos salvo limitación deliberada y documentada. La presentación y el mecanismo de persistencia pueden variar; dominio, campos y acciones deben seguir alineados.
23. **POS Sync acotado y separado de Customer.** Se reutilizan los principios probados de outbox atómico, UUID estable, comparación de versión Cloud, cursor incremental y resolución de conflictos, pero POS tiene sus propias tablas y puertos. Customer Sync no cambia de semántica ni de esquema. El orden del ciclo es Customer → ProductCategory → Product → Sale.
24. **Conflictos ProductCategory/Product.** El `updated_at` monotónico de Cloud es la versión de comparación; Desktop conserva `cloud_updated_at`. Un UPDATE solo procede si coincide esa versión. En una divergencia se mantiene la edición local y el snapshot remoto en `pos_sync_outbox`; la UI muestra ambos valores antes de elegir Desktop o Web. La resolución consulta Cloud de nuevo y exige otra revisión si volvió a cambiar. Conservar Desktop reintenta con la versión Cloud actual; conservar Web aplica el pull sin outbox. Un error de unicidad de barcode entre UUID distintos deja la operación pendiente y visible como error hasta corregir el catálogo.
25. **Venta como unidad inmutable.** Sale y todas sus SaleItems se suben mediante una RPC `SECURITY DEFINER` que valida `auth.uid()`, membership, integridad y sumas, y confirma o revierte todo en una transacción. El UUID y el contenido se verifican al reintentar. El pull aplica la venta completa mediante una transacción SQLite y avanza el cursor solo tras aplicarla. SaleItem no tiene cursor independiente; siempre viaja con Sale. Los clientes autenticados no tienen INSERT directo ni UPDATE de ventas completadas.
26. **Cloud POS y disponibilidad.** Web usa exclusivamente sesión normal y RLS; no guarda ventas offline ni emplea `service_role`. Desktop opera sobre SQLite incluso sin red y pausa sync hasta validar la sesión. La migración Cloud del POS base y la nueva migración POS Sync quedan pendientes de aplicación remota; un dry-run no equivale a validación SQL.
