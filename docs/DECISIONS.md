# Decisiones arquitectónicas aprobadas

1. **Dos clientes en un workspace pnpm.** Desktop usa Tauri 2; Web usa Vite con soporte PWA. Comparten `domain`, `application`, `ui` y `features` para evitar duplicación.
2. **Persistencia por plataforma.** SQLite local es la fuente primaria de operación de Desktop. Supabase/PostgreSQL es la fuente central compartida para Web; las lecturas cliente están sujetas a autenticación y RLS.
3. **Separación mediante puertos.** `application` define contratos; cada app aloja su adaptador concreto. `domain` permanece en TypeScript puro, sin React, Tauri, SQLite ni Supabase.
4. **Modelo incremental.** Sprint 1 creó `app_meta`; Sprint 2 añade solo Business, Branch y Device. Las entidades futuras considerarán `business_id`, `branch_id` y, para sincronización, `device_id` cuando corresponda.
5. **Sincronización diferida hasta Sprint 5.** Los primeros sprints documentaron Desktop SQLite ↔ Supabase sin implementarlo. Sprint 5 lo concreta únicamente para Customer.
6. **Sucursal obligatoria para Device.** Cada Device pertenece a una Branch del mismo Business; una FK compuesta impide vínculos cruzados. No hay razón actual para permitir dispositivos sin sucursal.
7. **Identificadores y tiempos.** UUID generables localmente permiten identidad offline. Cloud guarda `timestamptz`; Desktop guarda UTC ISO 8601. La instalación Desktop posee un UUID persistente separado del ID del registro Device.
8. **RLS cerrada hasta autenticación en Sprint 2.** Las tablas Cloud habilitaron RLS y revocaron acceso a `anon` y `authenticated`. La migración de autenticación concede únicamente lectura bajo políticas por membership. El seed se limita a desarrollo y no se aplica automáticamente al remoto.
9. **Bootstrap Desktop provisional de Sprint 2.** El adaptador local puede crear CentroColor, Sucursal principal y Device locales, pero dejó de ejecutarse al abrir la UI tras incorporar autenticación. Las filas anteriores se conservan; el contexto autorizado actual usa IDs Cloud.
10. **Identidad Cloud y límite multiempresa.** Supabase Auth identifica usuarios; memberships activos otorgan acceso a negocios y portan uno de tres roles iniciales. En las tablas de identidad, el cliente solo lee bajo RLS. El alta y cambio de roles son tareas administrativas manuales por ahora.
11. **RLS sin recursión.** Un helper en esquema `private`, con `SECURITY DEFINER`, `search_path` vacío y `auth.uid()`, comprueba membership activo. El esquema no se expone por API y la función solo se concede a `authenticated`.
12. **Autorización offline Desktop.** Tras login Cloud exitoso se guarda un resumen del contexto en SQLite; el siguiente inicio lo usa explícitamente como `offline-authenticated`. No se guarda sesión/token Desktop, por lo que revalidar exige login online. La copia local puede quedar obsoleta por revocación remota y no tiene protección de RLS.
13. **Clientes como primera entidad operativa.** Customer y sus reglas viven en domain; application define un único puerto y casos de uso. Web usa Supabase bajo RLS y Desktop usa SQLite local. La UI compartida recibe el puerto, usa el BusinessContext y limita la lista a 100 filas.
14. **Referencia local a negocio autorizado.** `customers.business_id` en Desktop no tiene FK a `businesses` local: el contexto validado trae IDs Cloud que pueden no coincidir con las entidades provisionales locales. Los adaptadores filtran toda operación por negocio. La migración Cloud sí tiene FK y RLS.
15. **Outbox atómico y acotado.** SQLite registra cambios Customer mediante triggers en la misma sentencia de escritura. Una fila por entidad compacta mutaciones consecutivas; `local_revision` impide reconocer por accidente una edición posterior al push. La infraestructura tiene campos mínimos reutilizables, pero solo sincroniza Customer.
16. **Versión Cloud y conflictos explícitos.** PostgreSQL gobierna `customers.updated_at`; Desktop guarda la última versión Cloud conocida y compara antes de actualizar. Los cambios concurrentes crean un conflicto local, sin sobrescritura silenciosa. La UI permite elegir la versión local o Web consultando Cloud de nuevo; conservar local usa comparación optimista otra vez.
17. **Pull incremental por negocio.** Cursor persistido `(updated_at, id)` y páginas limitadas. PostgreSQL asigna versiones monotónicas bajo un bloqueo de fila en `private.customer_sync_clock` por negocio para que el orden de commit no deje huecos; el cursor compuesto también cubre empates de filas previas. El cursor avanza después de aplicar o registrar cada fila. La sesión Cloud y el membership se revalidan antes de cada ciclo; el contexto offline permite operar SQLite, pero no sincronizar.
18. **POS local primero.** Sprint 5 opera Product, ProductCategory, Sale y SaleItem en SQLite Desktop. El esquema Cloud existe para evolución futura, sin adaptador Web ni sincronización de estas entidades. `sync_outbox` y el indicador existente continúan siendo exclusivos de Customer.
19. **Ventas atómicas e históricas.** El comando Tauri `complete_local_sale` escribe Sale y SaleItems en una transacción SQLite con validación de suma y foreign keys. Los ítems guardan snapshots de nombre, barcode y precio; ventas completadas no se editan. La referencia visual es un prefijo de UUID, sin semántica fiscal ni secuencia Cloud.
20. **Centavos enteros y stock por sucursal.** Los contratos usan enteros seguros de centavos y la entrada decimal se convierte mediante BigInt. Product no incluye stock global; Sprint 7 lo modela por sucursal. El `device_id` de Sale es nullable hasta disponer de una asociación confiable entre instalación y Device Cloud.
21. **FK multiempresa de Sale a Device.** La migración Cloud pendiente garantiza una clave UNIQUE `(business_id, id)` para respaldar la FK compuesta de `sales`. La PK de `devices.id` no alcanza como clave referenciada para ese par. El remoto contiene una relación llamada `devices_business_id_id_unique` que no proviene de las migraciones anteriores versionadas; su origen exacto no puede determinarse con el repositorio. La migración comprueba en `pg_index` si ya existe una clave única válida, inmediata y no parcial sobre las dos columnas. Si falta, crea la constraint `devices_business_id_id_pos_unique`. No elimina objetos remotos ni cambia la migración de identidad aplicada.
22. **Paridad permanente Desktop/Web.** Ambos clientes son el mismo sistema. Una capacidad importante debe existir en ambos salvo limitación deliberada y documentada. La presentación y el mecanismo de persistencia pueden variar; dominio, campos y acciones deben seguir alineados.
23. **POS Sync acotado y separado de Customer.** Se reutilizan los principios probados de outbox atómico, UUID estable, comparación de versión Cloud, cursor incremental y resolución de conflictos, pero POS tiene sus propias tablas y puertos. Customer Sync no cambia de semántica ni de esquema. El orden del ciclo es Customer → ProductCategory → Product → Sale.
24. **Conflictos ProductCategory/Product.** El `updated_at` monotónico de Cloud es la versión de comparación; Desktop conserva `cloud_updated_at`. Un UPDATE solo procede si coincide esa versión. En una divergencia se mantiene la edición local y el snapshot remoto en `pos_sync_outbox`; la UI muestra ambos valores antes de elegir Desktop o Web. La resolución consulta Cloud de nuevo y exige otra revisión si volvió a cambiar. Conservar Desktop reintenta con la versión Cloud actual; conservar Web aplica el pull sin outbox. Un error de unicidad de barcode entre UUID distintos deja la operación pendiente y visible como error hasta corregir el catálogo.
25. **Venta como unidad inmutable.** Sale y todas sus SaleItems se suben mediante una RPC `SECURITY DEFINER` que valida `auth.uid()`, membership, integridad y sumas, y confirma o revierte todo en una transacción. El UUID y el contenido se verifican al reintentar. El pull aplica la venta completa mediante una transacción SQLite y avanza el cursor solo tras aplicarla. SaleItem no tiene cursor independiente; siempre viaja con Sale. Los clientes autenticados no tienen INSERT directo ni UPDATE de ventas completadas.
26. **Cloud POS y disponibilidad.** Web usa exclusivamente sesión normal y RLS; no guarda ventas offline ni emplea `service_role`. Desktop opera sobre SQLite incluso sin red y pausa sync hasta validar la sesión. Las migraciones Cloud POS figuran aplicadas en el historial remoto consultado el 21/9/2026; falta prueba operativa real. Un dry-run no equivale a validación SQL.
27. **Assets de Desktop embebidos en release.** La configuración Tauri base usa `frontendDist: ../dist` y genera únicamente NSIS en Windows. `devUrl` y el comando Vite están en `tauri.dev.conf.json`, que recibe solo `pnpm dev:desktop` mediante `--config`. El build Vite usa rutas relativas para sus assets. Así el ejecutable de distribución no contiene la URL de desarrollo y no necesita servidor local.
28. **Inventario por Branch y ledger.** El stock pertenece a Business+Branch+Product. `stock_movements` es el historial inmutable y unidad primaria de sync; `inventory_balances` se materializa mediante trigger transaccional y nunca se sincroniza como valor mutable. Cantidades son enteros; negativos se admiten con aviso en POS.
29. **Alta segura y sin backfill.** `tracks_inventory=false` para Product existente y `sale_items.tracks_inventory=false` para ventas previas. El usuario establece stock inicial por conteo real. Un conteo inicial cero activa tracking sin crear un movimiento delta cero. Desactivar tracking no elimina movimientos.
30. **Venta y movimiento con identidad única.** SaleItem guarda el snapshot de tracking. Si es verdadero, el INSERT de la línea crea movimiento `sale` con el mismo UUID que SaleItem. El trigger de ledger actualiza balance en la transacción de checkout. Sale Sync conserva ese UUID y el push posterior del outbox de stock reconoce el movimiento Cloud; por eso un retry no descuenta dos veces.
31. **Cursor Cloud de movimientos.** `received_at` se asigna en Cloud con el reloj serializado POS por negocio. El pull usa `(received_at,id)`, nunca `occurred_at` del equipo. SQLite inserta solo UUID ausentes y no genera outbox al recibir movimientos remotos. Un inicial concurrente desde dos dispositivos genera un error visible pendiente para revisión; no se fusionan dos conteos físicos automáticamente.
32. **Permisos de inventario.** Owner/admin realiza movimientos manuales y cambia tracking; staff consulta y vende. Desktop valida el contexto autorizado local; Cloud revalida auth/membership/rol y relaciones Branch/Product en RPC con `search_path` seguro. La autorización offline puede quedar obsoleta hasta reconectar, conforme a la decisión 12.
33. **Appointment no es Event.** Appointment representa una cita sencilla con cliente, sucursal, intervalo, título y estado. Events extensos, servicios contratados y reservas de recursos tendrán identidades y ciclos propios; no se agregan ahora como campos opcionales del turno.
34. **Plantilla desacoplada del título.** AppointmentType configura nombre y duración predeterminada, sin precio ni catálogo de servicios. Appointment guarda un título obligatorio editable; renombrar o desactivar el tipo no cambia el texto histórico del turno.
35. **Tiempo absoluto y presentación local.** Web y Desktop convierten la entrada local a ISO UTC; Cloud usa `timestamptz` y SQLite texto ISO. La UI convierte el instante a la zona del dispositivo/usuario. No se fija `-03:00` en dominio ni migraciones. Incorporar una zona IANA explícita por negocio queda como evolución si el sistema debe operar sucursales en zonas diferentes.
36. **Superposición advertida, no bloqueada.** Solo turnos `scheduled` de la misma Branch participan en la advertencia por intervalo semiabierto. Cancelados, completados y ausentes no bloquean. El usuario puede confirmar para contemplar trabajo paralelo; no se modela todavía agenda por fotógrafo o recurso.
37. **Sync mutable y separado de Agenda.** AppointmentType y Appointment usan UUID estable, outbox propio, cursor `(updated_at,id)`, reloj monotónico Cloud y comparación optimista. Los estados y reprogramaciones son updates del mismo UUID. El pull remoto nunca genera outbox. Los conflictos conservan local y snapshot Cloud hasta resolución explícita.
38. **Permisos iniciales de Agenda.** Membership activo puede leer agenda; owner/admin gestiona tipos y transiciones hacia/desde cancelado. Staff crea, edita, completa y marca ausente. Business/Branch vienen de contexto y FK compuestas Cloud impiden Customer o AppointmentType de otro negocio. No se concede DELETE.
39. **Event no es Appointment.** Event modela actividades extensas, lugar, servicios contratados y recursos con horarios propios. Appointment conserva su ciclo de cita corta y no recibe campos opcionales de Events.
40. **Resource no es Product.** Cada Resource es una unidad física reservable y configurable. No participa en inventario, stock, POS ni `quantity_available`; dos unidades reales son dos UUID distintos.
41. **Snapshots de servicio y total derivado.** EventServiceItem guarda nombre, descripción, cantidad y precio históricos, con `source_service_id` nullable para un catálogo futuro. El total se deriva en centavos enteros de servicios y reservas activas; no se modelan pagos ni señas.
42. **Disponibilidad por intervalo y estado.** ResourceReservation posee un intervalo independiente del Event. Se usa intersección semiabierta; contiguas no solapan. Sólo Events `reserved` y `completed` bloquean. Cancelar libera sin borrar; `quoted` no bloquea.
43. **Cloud como autoridad física.** PostgreSQL serializa escrituras mediante advisory lock por Business+Resource y valida en triggers transaccionales tanto reservas como transiciones a estados bloqueantes. Web y Desktop sync pasan por la misma garantía; la UI es sólo una validación anticipada.
44. **Conflicto offline explícito.** SQLite valida contra datos conocidos. Si Cloud ya aceptó una reserva superpuesta, el push o pull marca la reserva local con conflicto de disponibilidad, conserva ambos registros y exige editar/desactivar localmente. No existe override silencioso en Sprint 9.
45. **Sync separado de Eventos.** `event_sync_outbox` y cursores cubren `EventType → Resource → Event → EventServiceItem → ResourceReservation`, después de Customer. Items/reservas usan `is_active` para converger sin DELETE; el pull remoto no genera outbox.
46. **Medida opening y cálculo de marquetería.** `opening` es siempre la medida interior útil, en mm enteros. La longitud de corte inicial de varilla es `2 × ((ancho + frente) + (alto + frente))`, seguida de merma porcentual con redondeo hacia arriba; el frente puede ser cero si aún no se configuró. Materiales de superficie usan `ancho × alto` en mm² y convierten al facturar por m². Markup es sobre costo, no margen de venta. Las cotizaciones guardan líneas snapshot y no cambian por futuros catálogos/precios.
47. **Inventario de marquetería diferido.** Sprint 10 no descuenta Product/Inventory al cotizar ni entregar. La gestión de barras, metros restantes, retazos y optimización de corte requiere un modelo dedicado posterior.
48. **Sync y permisos de Marquetería.** Las seis entidades usan outbox, UUID estable, cursor `(updated_at,id)`, comparación optimista y pull con origen remoto. Catálogos y configuración se restringen a owner/admin; staff los consulta y puede cotizar/operar trabajos. La fórmula opening vigente queda pendiente de validación operativa del método real de corte.
49. **PhotoJob es un ciclo productivo propio.** Appointment es cita, Event es actividad extensa/reserva y FrameJob es producción de marquetería. PhotoJob requiere Customer y modela recepción, producción, listo, entrega o cancelación. Las referencias a Appointment/Event son opcionales y no disparan conversiones automáticas.
50. **PhotoService no es Product.** Los servicios fotográficos no son artículos inventariables del POS. Cada variante/tamaño puede tener su propio registro y precio; PhotoJobItem congela nombre, dimensiones y precio, y admite una línea custom con `photo_service_id` nulo.
51. **Total derivado y sin pagos.** El total de PhotoJob se deriva exclusivamente de items activos, con cantidad entera y centavos enteros. Sprint 11 no agrega señas, cobros, facturación ni integración PhotoJob→Sale.
52. **Sync separado de Fotografía.** `photo_sync_outbox` y cursores cubren `PhotoService → PhotoJob → PhotoJobItem`, después de Customer/Appointment/Event. Los tres tipos son mutables con comparación optimista; una transición de estado divergente queda en conflicto con snapshot remoto y nunca se sobrescribe silenciosamente.
53. **Permisos de Fotografía.** Owner/admin administra el catálogo; staff lo consulta. Todo membership activo crea y opera trabajos. RLS y FK compuestas aíslan Business; no hay DELETE ni `service_role`. El storage de imágenes queda explícitamente fuera del modelo.
54. **Ledger común de trabajos.** Event, FrameJob y PhotoJob comparten `WorkPayment`; no existen tres tablas de pagos. La fuente usa tres FK reales con exactamente una presente y `source_type` coherente. Sale/POS permanece separado hasta diseñar explícitamente una integración futura.
55. **Pago append-only y anulación auditada.** Deposit, payment y refund son movimientos positivos por tipo. Un pago histórico no cambia importe, fuente, fecha ni medio; corregirlo exige `posted → voided` con actor, fecha y motivo, y eventualmente un nuevo movimiento. Cancelar la fuente no altera el ledger.
56. **Cloud decide el último saldo.** `post_work_payment` adquiere advisory lock por fuente, calcula el neto dentro de la transacción y bloquea sobrepago/refund excesivo antes del INSERT. Los clientes no reciben grants directos de mutación. Staff cobra; sólo owner/admin anula.
57. **Conflicto financiero offline conservado.** SQLite permite cobrar y devolver contra su última copia. El sync se ordena después de las fuentes y reintenta por UUID. Si Cloud rechaza por saldo concurrente, la fila local queda en conflicto, deja de afectar el saldo operativo local y sólo owner/admin puede descartarla mediante anulación; nunca se borra físicamente.
58. **Drive es autoridad binaria.** Los archivos de cliente se guardan una sola vez en Google Drive. PostgreSQL y SQLite contienen sólo metadata; Supabase Storage, outbox y cursores nunca transportan bytes.
59. **OAuth y Vault son server-side.** La aplicación usa scope `drive.file`. Client secret, access token y refresh token nunca llegan al portal ni a variables `VITE_`; Vault conserva el refresh token y las Edge Functions lo intercambian por access tokens efímeros.
60. **Token capability limitado.** El portal usa 32 bytes aleatorios codificados URL-safe y persiste sólo SHA-256. Expiración, revocación, link cerrado y asociación a un único PhotoJob se verifican en cada endpoint. Los destinos de item son opacos y se vuelven a resolver contra el Job autorizado.
61. **Ingreso separado de producción.** `file_intake_status` no reutiliza `PhotoJob.status`. Finalizar archivos no mueve automáticamente el Job a `in_progress` o `ready`.
62. **Routing configurable.** `workflow_route` y `requires_customer_files` pertenecen a PhotoService; no se deducen de `service_type`. `PhotoJobFile` conserva la ruta usada al cargar para que la cola histórica no cambie por una edición posterior del catálogo.
63. **Carpetas por ID e idempotencia.** La jerarquía visible se crea con nombres sanitizados, pero identidad y retries usan Drive IDs, `appProperties` y `photo_job_drive_folders`. `Editadas` se crea cuando existe un destino editing.
64. **Cierre controlado.** Al finalizar, el link queda cerrado mediante `submitted_at`. Para agregar archivos se regenera un link y el anterior se revoca. El submit y finalize son idempotentes.
65. **Desktop metadata-only.** Desktop puede operar trabajos offline, pero no subir/cachar fotos. Extiende el sync mutable de PhotoService/PhotoJob y hace pull de PhotoJobFile sin outbox local; abrir Drive requiere Internet.
66. **OAuth state confirmado y consumo transaccional.** Start no entrega una URL Google hasta confirmar que el state hasheado quedó persistido con una ventana de 600.000 ms usando privilegios server-only explícitos. Callback diferencia lookup fallido, inexistente, consumido y vencido. Después de intercambiar el código, guardar el refresh token en Vault y resolver la carpeta raíz, una RPC con lock persiste la integración y marca `consumed_at` en la misma transacción. Antes de esa RPC el intento puede reintentarse o abandonarse hasta vencer; después, un callback repetido se rechaza. Los logs usan sólo request ID, fingerprint SHA-256 truncado, estados y metadata temporal.
67. **`service_role` no recibe privilegios implícitos.** En este proyecto las tablas nuevas de `public` no se exponen automáticamente a los roles de la Data API: `service_role` sólo tenía REFERENCES/TRIGGER/TRUNCATE, así que toda lectura devolvía vacío y toda escritura fallaba con 42501. Cada tabla que una Edge Function toca necesita un GRANT explícito y mínimo en una migración (SELECT sobre datos de Job/Customer/Business/servicios, UPDATE por columnas sobre `photo_jobs`, DML sobre las tablas de intake, nunca DELETE). Un test de contrato compara las tablas y RPC que usa el código Edge contra los GRANT de las migraciones. Complementa 53: Fotografía sigue sin acceso `anon` y los clientes sin DELETE, pero las Edge Functions de archivos usan `service_role` de forma acotada.
68. **Contrato único de Edge Functions.** Handlers puros con dependencias inyectadas (`store`, `drive`, `getEnv`) y entrypoints de una línea. Admin: JWT → usuario → membership activa → rol owner/admin → recién entonces se crean los servicios con `service_role`. Público: el token es una capability que se resuelve por SHA-256 a un único Link→Business→Job en cada request. Los errores curados son `ApiError(status, code)`; cualquier otro error (base de datos incluida) se registra con operación, código SQLSTATE y `requestId` y el cliente recibe un mensaje genérico con `requestId`. El estado HTTP ya no se deduce de palabras del mensaje. Los fallos de Drive/configuración del negocio se ocultan al cliente final (503 genérico) y se muestran completos a owner/admin.
69. **Columnas de intake pertenecen al servidor.** Web y Desktop empujan filas completas de PhotoJob; para impedir que un valor desactualizado reabra un Job ya enviado, un trigger BEFORE UPDATE conserva `file_intake_status`, `drive_folder_id` y `drive_edited_folder_id` cuando el rol es `authenticated`/`anon`. INSERT y `service_role` no cambian. Consecuencia: `setFileIntakeStatus` desde clientes ya no tiene efecto sobre un Job existente; el estado cambia sólo mediante las Edge Functions.
70. **Triggers compartidos sin expresiones multi-tabla.** `photo_guard_immutable_identity` mezclaba campos de `photo_jobs` y `photo_job_items` en una sola expresión booleana; PostgreSQL no garantiza cortocircuito en AND, por lo que todo UPDATE de PhotoJob/PhotoJobItem/PhotoService fallaba con 42703. La corrección ramifica por `tg_table_name`. Regla: una función de trigger compartida nunca referencia `NEW.campo` específico de una tabla dentro de una condición compuesta.
71. **Resumable directo desde el navegador.** La sesión se abre desde el servidor reenviando el `Origin` del navegador (Google sólo responde CORS al PUT del navegador para el origen con que se creó la sesión). El cliente reintenta errores de red/429/5xx consultando el offset confirmado, tolera que `Range` no sea legible por CORS (asume el chunk aceptado) y `finalize` verifica ID, parent, nombre y tamaño en Drive como red de seguridad. Las `appProperties` de Drive limitan clave+valor a 124 bytes, por eso nunca llevan texto del usuario. El límite por Job es 500 archivos activos (los `failed` no cuentan) y 120 sesiones por minuto. Pendiente de confirmar en navegador real: CORS del PUT.
72. **Sólo `invalid_grant` exige reconexión.** Un refresh token rechazado por `invalid_grant` marca `reconnect_required`; credenciales inválidas, red o caídas de Google no desconectan la integración. La configuración (`PHOTO_UPLOAD_SIGNING_SECRET`, URL pública, días, bytes máximos, credenciales Google) se valida en el punto de uso y el error nombra la variable, nunca su valor.
73. **El pedido público es otro canal de entrada al MISMO PhotoJob.** `photo_jobs.source_channel` (`manual`, `public_web`, `future_gmail` —reservado—) distingue el origen; el modelo, Producción, pagos y sync son los de siempre. El flujo manual «Generar link» no cambia. Un pedido web es un borrador (`is_draft`) hasta confirmarse: RLS oculta a cualquier rol cliente el trabajo, sus items y sus archivos mientras sea borrador, de modo que Producción, Trabajos, Dashboard y el pull de Desktop sólo ven pedidos confirmados. Los borradores no se borran; `cc_public_order_mark_abandoned(interval)` los marca y revoca sus links bajo una política manual. `is_draft` y `source_channel` son columnas de servidor (un trigger las conserva ante UPDATE de roles cliente y la policy de INSERT las fija en `false`/`manual`).
74. **El servidor decide el dinero.** El navegador envía sólo `serviceId` y cantidad (más el total que vio, únicamente para detectar una lista de precios vieja). El servidor relee `photo_services`, calcula y la transacción SQL verifica de nuevo el precio esperado contra el catálogo (`cc_error:price_changed`). El snapshot (nombre público, precio, dimensiones) se toma al iniciar y queda congelado al confirmar; cambios futuros del catálogo no tocan pedidos históricos. La cantidad final de cada item se **deriva** de `sum(PhotoJobFile.copies)` en la confirmación; un tamaño sin fotos queda inactivo.
75. **Dos capacidades distintas sobre una misma tabla.** `photo_job_upload_links.purpose`: `upload` (mutación de archivos, 14 días, un solo uso para confirmar) y `tracking` (sólo lectura del estado, 180 días). Mismo token aleatorio de 32 bytes con sólo SHA-256 en base, revocable y limitado a un Job, pero cada endpoint valida el propósito: subir/confirmar rechaza `tracking` y seguir rechaza `upload`. Revocar o regenerar links de subida nunca toca los de seguimiento. Como el texto plano no se guarda, cada mensaje de WhatsApp acuña un link de seguimiento propio.
76. **Idempotencia por clave del navegador.** `public_photo_orders(business_id, client_key)` es única; `cc_public_order_start` serializa con advisory locks por clave y por teléfono y es una única transacción (Customer + job + items + order + link). Repetir la clave sobre un borrador reutiliza todo y rota el link de subida; sobre un pedido enviado responde `submitted`. La confirmación (`cc_public_order_confirm`) es idempotente: repetirla no duplica nada y emite otro link de seguimiento.
77. **Customer: coincidencia derivada, sin reescribir historia.** `customers.phone_match_key` es una columna generada (últimos 10 dígitos) con índice; el pedido reutiliza el Customer activo del negocio con esa clave y nunca lo modifica ni lo expone. Teléfonos históricos con «15» intercalado pueden no coincidir (se prefiere un duplicado a fusionar personas distintas). `Customer` se crea al iniciar la subida porque el trabajo lo exige.
78. **Teléfonos normalizados en el servidor con `libphonenumber-js`** (metadatos `max`, import `npm:` pineado en Deno y alias en Vitest). País por defecto Argentina; los celulares argentinos se canonizan como `+549…` para que el mismo número escrito de distinta forma dé el mismo E.164. Se guarda el snapshot usado para el pedido (`public_photo_orders.whatsapp_e164`); cambiar `Customer.phone` después no reescribe a quién se debía avisar.
79. **Consentimiento transaccional por pedido.** Casilla visible y tildada por defecto («avisos relacionados con este pedido»); se guarda opt-in, timestamp y `consent_source = 'public_order'` en el pedido. No se reutiliza para marketing y los pedidos manuales no generan avisos.
80. **OutboundNotification durable e idempotente por trigger.** Un trigger AFTER UPDATE de `photo_jobs` (transición a `ready`) inserta `photo_job:<id>:ready:whatsapp` con `UNIQUE(business_id, idempotency_key)` y `ON CONFLICT DO NOTHING`; así `ready → in_progress → ready` no duplica y el origen del cambio (Web, sync de Desktop, SQL) es irrelevante. Está envuelto en un bloque que captura todo error: jamás impide cambiar el estado. Sin integración configurada el aviso nace `failed` (`integration_not_configured`/`integration_error`) y se reintenta con un clic. Retry reutiliza la fila; reenviar crea una fila nueva `manual_resend` con su propia clave (máx. 5 por trabajo). Toda transición queda en `outbound_notification_events`. No hay DELETE ni UPDATE directo para ningún rol.
81. **El token de WhatsApp sólo existe en Vault.** `whatsapp_integrations` guarda `access_token_secret_id`; ningún rol cliente puede leer la tabla y la función `whatsapp-admin` nunca devuelve token ni id de secreto. Owner/admin configura; cualquier miembro opera (reintentar/reenviar). El estado `error` se fija cuando Meta rechaza el token o el número.
82. **El envío lo hace la nube, nunca un dispositivo.** Desktop no llama a Meta: el estado `ready` sincronizado dispara el trigger y `whatsapp-dispatch` (secreto compartido) envía. Para que sea inmediato, el trigger despierta al emisor con `pg_net` y dos secretos de Vault (opcional; sin ellos queda `pending`). Un envío reclamado pasa a `sending` de forma atómica (`FOR UPDATE SKIP LOCKED`); uno interrumpido se marca `failed`, no se reenvía solo. `sent` significa «Meta aceptó»; `delivered`/`read` sólo con el recibo firmado del webhook y nunca retroceden.
83. **Portal anónimo con límites propios.** Sólo JPG/PNG/HEIC/TIFF, 100 MB por foto y 200 fotos por pedido; rate limit por hora global, por dirección de cliente (hash con el secreto de firma) y por teléfono; honeypot; nombre y notas acotados. Los mensajes al cliente no mencionan Drive, Supabase ni términos técnicos. `photo_jobs.created_by` sigue siendo NOT NULL (y espejado en SQLite): el creador técnico del pedido web es el owner; el origen real es `source_channel`.
84. **La base real entra en las pruebas.** Además del contrato estático de grants (ampliado con las tablas nuevas) se ejecutan las migraciones en PGlite: RPC, triggers, RLS y grants SQL son los publicados, y los stores de las Edge Functions corren sin cambios contra ellos con el rol correspondiente. Un dry-run o un grep de SQL no equivalen a validación real.
85. **DESIGN-01 es una propuesta aislada, no una decisión adoptada.** `apps/design-preview` (React/Vite, solo `react`/`react-dom`) vive fuera de `domain/application/ui/features`, con mocks en memoria y sin ninguna dependencia de infraestructura. Propone navegación de 11 módulos, tokens (amarillo `#FFC914`, grafito, crema, rojo del logo), tipografías Bricolage Grotesque/Figtree/DM Mono alojadas localmente y un flujo de pago por transferencia previo a la impresión que **contradice** el Sprint 14 (pago en el local) hasta que se decida. Nada de esto está aprobado para producción.
86. **DESIGN-02 mantiene la preview aislada y fija reglas de ruido.** Misma identidad, otra jerarquía: amarillo sólido solo para navegación activa/CTA/selección/aviso, bordes finos y sombra dura solo en CTA y carrito, un estado principal por fila (el resto como texto), contadores de navegación solo si exigen atención y copy solo si decide, evita un error o explica una consecuencia. El portal quitó la casilla de aviso por WhatsApp (el consentimiento queda como pendiente legal antes de producción). Sigue sin aprobarse para producción.
87. **DESIGN-02 es la dirección visual de producción; la preview queda como referencia.** El sistema (tokens, tipografías alojadas, componentes, shell, portal) vive en `packages/ui` y `apps/web/src/public-order`; `apps/design-preview` no se elimina ni se despliega. Web y Desktop comparten CSS y componentes: no hay estilos por plataforma. Desktop no inlinea assets ni usa `data:` (CSP de Tauri). Los colores salen de tokens; las features conservan sus clases (`legacy.css`, repintadas con tokens) y migran a componentes compartidos de a poco.
88. **Navegación por módulos con pestañas, sin perder rutas.** Las 22 entradas planas pasan a 11 módulos agrupados; cada vista anterior sigue siendo alcanzable como pestaña del módulo (test de navegación). Los contadores existen sólo para atención real (trabajos atrasados en rojo, cobros con trabajo terminado y saldo, productos sin stock); nada cuenta «listos» ni totales. Se agregó la vista `payments` (Cobros) y se quitó del menú el placeholder `services`, que sigue resoluble.
89. **El portal sólo promete lo que el backend hace.** El pago sigue siendo en el local: el paso 3 del hero es «Confirmá» y la aclaración comercial es «El pago se realiza en el local al retirar tu pedido». El copy de DESIGN-02 («Transferí», «Se imprime una vez acreditada la transferencia») queda detrás de `PAYMENT_MODE = 'transfer'` y no se enciende hasta que exista el gate de pago, el estado «esperando transferencia» y la acción de confirmación. Se conserva la casilla de consentimiento de WhatsApp ya existente. `/imprimir/recibido` es la dirección de la pantalla de confirmación; recargarla lleva al seguimiento del último pedido del navegador.
90. **Cobros es una vista del ledger existente.** La bandeja usa `WorkPaymentRepository.listOutstanding` y abre `PaymentAccountPanel` (Total/Pagado/Saldo/Historial, registrar pago/seña/devolución, anular); no crea estados ni medios nuevos. Producción gana las acciones En proceso/Listo (`setJobStatus`, con el mismo aviso a la nube que el detalle del trabajo) para la tablet de laboratorio, sin ruta nueva.
91. **Marquetería: la varilla es el perímetro de la abertura.** `mouldingLengthMm = 2 × (ancho + alto)` más merma; `faceWidthMm` es metadata descriptiva y no consume (30 × 40 cm → 1400 mm; vidrio/fondo 0,12 m²). Cambia sólo el cálculo de presupuestos nuevos: los guardados conservan su snapshot. Es el único cambio de dominio de la adopción de DESIGN-02.
92. **El escáner es una capacidad global del panel.** Un único listener en `PanelShell` (nunca en rutas públicas) reconoce ráfagas HID por timing y terminador; la resolución reutiliza `scanBarcode` y el carrito sigue siendo del POS (cola de productos que el POS retira). Producto desconocido → alta en Productos con barcode bloqueado → al guardar, POS con 1 unidad. Ante modal, alta en curso o campo con texto, el escaneo se descarta con aviso en lugar de arriesgar datos sin guardar.
